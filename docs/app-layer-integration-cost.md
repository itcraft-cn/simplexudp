# 应用层接入 simplexudp 的代价评估

日期：2026-10-02　基线：`e466fa7`（含代码审查修复后的 simplexudp）

## 0. 结论摘要

- **调用 SX API 本身的成本很低**：一个薄适配层通常几十~几百行；p2p 小消息场景 0.5~2 人日即可跑通。
- **真正的成本在“应用层要自己补齐的语义”**：分片/重组、请求响应、topic/订阅、安全、事件循环对接等，SX 不提供。
- 若你的“应用层”是 **pub/sub（topic 订阅式分发）**，SX 只是**可靠传输**，topic/订阅/过滤是主要工程量（1~3 人周量级）。
- SX 与 UDP 后端同构：**开发用 UDP、生产切 XDP**，切换成本≈配置项，显著降低接入与联调成本。

## 1. 定位

```
应用层（业务语义：topic/订阅、RPC、编解码、安全）   ← 主要工程量
        │  sx_send / sx_recv / on_recv
simplexudp（可靠有序、丢包侦测重发、p2p/组播/广播）  ← 已实现，API 简单
        │
XDP/AF_XDP（生产） 或 内核 UDP（开发）             ← 配置切换
```

“xdp+应用层”= SX 提供 XDP 数据面与可靠消息传输，应用层负责业务语义。

## 2. 接入面（必须做，成本低）

| 事项 | 说明 | 成本 |
| --- | --- | --- |
| 生命周期 | `sx_config_init → sx_create → sx_start → … → sx_stop/sx_destroy` | 极低 |
| 配置 | `ifname/backend(AUTO/XDP/UDP)/local_ip/local_port/conv/max_payload/窗口` | 低 |
| 事件循环 | `sx_wait + sx_update`（或 `sx_run`，或 `rx_thread=1`） | 低 |
| 收发 | `sx_send` / `on_recv` 或 `sx_recv`；处理 `SX_ERR_WINDOW` 背压 | 低 |
| 链路 | `sx_add_unicast/multicast/broadcast`、自动学习、`sx_link_remove` | 低 |
| 日志 | `on_log` 回调（库不写 stdout/stderr） | 极低 |
| 观测 | `sx_get_stats`、`bpftool`（XDP） | 低 |

## 3. 应用层需自建的能力（主要成本来源）

| 需求 | SX 是否提供 | 应用层要做 | 成本 |
| --- | --- | --- | --- |
| 单包 ≤1426B | 提供（`sx_max_payload` 硬限） | >上限消息的**分片/重组**（序号+分片号+重组缓冲） | 中（1~2 人日） |
| 有序可靠 | 提供（逐链路） | 无（链路即端到端；中转场景需应用层端到端 ACK） | 低 |
| 消息编解码 | 不提供（payload 不透明） | 定义帧格式/序列化/版本 | 低~中 |
| 请求/响应(RPC) | 不提供 | 请求 id、超时、匹配、重试 | 中（3~5 人日） |
| 发布/订阅、topic | **不提供**（只有 `conv` + 组播/广播） | topic 表、订阅/退订、过滤、成员管理、扇出策略 | **高（1~3 人周）** |
| 组播/广播 | 提供（尽力可靠 + 有序） | XDP 后端需接口接受组；跨子网需应用层扇出 | 中 |
| 点对多 | 提供（多单播 peer / 组播 / 广播） | peer 发现、上限/清理、扇出背压 | 中 |
| 安全（鉴权/加密） | 不提供 | 会话鉴权、密钥、加密（或走可信网） | 中~高（1~3 人周） |
| 拥塞/多流公平 | 无跨流公平（每 link 一个 KCP） | 多流场景需应用层调度/限速 | 中 |
| 事件循环对接 | 有 `sx_wait`，**无 `sx_fd`** | 自有 reactor（epoll）集成需线程/轮询封装 | 中 |
| 零拷贝/批量 | 不提供（`sx_recv` 拷贝） | 高吞吐需等待库增强或在适配层凑合 | 视需求 |

## 4. 集成模式选择（影响成本与复杂度）

- **回调模式**：`on_recv` 直接处理。简单；`rx_thread=1` 时回调在库线程，需注意线程安全（库为递归锁，回调内可 `sx_send`）。
- **拉取模式**：`on_recv=NULL` + `sx_recv`。更适合与自有事件循环/框架（asyncio/Netty/自有 reactor）集成；需自己驱动 `sx_update`。
- **事件循环对接**：当前只能 `sx_wait(ep, timeout)` 阻塞等待或轮询；若应用已有 epoll，建议补 `sx_fd()`（见第 7 节）。
- **线程模型**：默认单线程 `update`；`rx_thread=1` 可把网络线程留在库内。`sx_link_remove` 后句柄失效，需避免与其他线程并发使用。

## 5. 后端切换成本（XDP vs UDP）

- 开发/CI：`SX_BACKEND_UDP`，**无需 root**，行为与 XDP 后端线格式一致。
- 生产：`SX_BACKEND_XDP`（`ifname` + `local_port` 必填；native 优先回退 generic；zero-copy 自动回退 copy）。
- 切换主要是配置与部署：
  - 需 root/CAP_BPF/CAP_NET_ADMIN、内存锁/ cgroup、把流量引导到绑定队列；
  - ARP 由库用户态处理，限同二层；组播需接口接受组；
  - 退出需 `sx_stop` 以 detach（异常退出残留需 `xdp-loader unload`）。
- 结论：**接入期用 UDP 后端几乎零成本；XDP 的代价在部署与环境**，不在应用代码。

| 场景 | 估计 |
| --- | --- |
| 基础 p2p（固定对端、≤1400、无分片） | 0.5~2 人日 |
| p2mp 多单播 / 星型扇出 | +1~3 人日 |
| 组播/广播发布（UDP 后端） | +1~2 人日 |
| 分片/重组（>1400 消息） | +1~2 人日 |
| 请求/响应（RPC） | +3~5 人日 |

| 安全（鉴权/加密） | +1~3 人周 |
| 性能调优（窗口/RTO/绑核/队列） | 视目标 +2~5 人日 |

## 7. 建议的库侧增强（能明显降低接入成本）

按性价比：

1. `int sx_fd(sx_endpoint_t*)`：暴露可 poll 的 fd → 直接并入应用 epoll/Selector，免额外线程/轮询。
2. 消息分片/重组：在 SX 层支持 >`max_payload` 的消息，省去每个应用自建。
3. 请求/响应与超时的便捷 API（可选）。
4. topic/订阅的“最小映射”：例如 `conv` 作为 topic/组标识 + 订阅 API（过滤仍在应用层）。
5. 批量收发与可选零拷贝收包（高吞吐场景）。
6. 可选鉴权/加密钩子。

## 8. 风险与注意

- **max_payload 与 MTU**：单包 ≤1426；超长必须分片。
- **背压**：`sx_send` 返回 `SX_ERR_WINDOW` 需重试/排队，不能忙等。
- **事件循环缺 fd**：无 `sx_fd` 时，自有 reactor 集成要么加线程，要么轮询。
- **组播在 XDP 后端**：需接口接受组（`ip maddr add`/allmulti），否则收不到。
- **多流与规模**：每 link 一个 KCP，peer 数量大时内存/CPU 线性增长（库已限 `SX_MAX_PEERS`）。
- **安全缺失**：默认无鉴权/加密，公网或不可信二层需自行加固。
- **部署**：AF_XDP 的权限、队列绑定、ARP、单队列限制等。

## 9. 推荐接入路径

1. **先 UDP 后端 + 拉取模式**打通：适配层实现“分片/重组 + 编解码 + 背压 + 事件循环”。
2. **按业务补语义**：p2p→p2mp→（如需）topic 订阅/RPC/安全。
3. **生产切 XDP**：仅改配置与部署，代码不变。
4. 同步推动库侧第 7 节增强（尤其 `sx_fd` 与分片），把共性成本沉到库，避免每个应用重复实现。
