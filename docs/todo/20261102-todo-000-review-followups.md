## 3. 核实中发现的额外问题

### 3.1 公共 API 的 `mac` 字段是“死字段”

`sx_addr_t.mac` 在头文件中被描述为“目的 MAC；XDP 后端可留 0，由 ARP 解析”，但：

- 添加链路时没有把 `mac` 写入 ARP 表；
- `xdp_sendto` 只走广播/组播映射或 `sx_arp_resolve`，不读取 `cfg`/`addr` 中的 MAC；
- `sx_arp_set` 只在内部头文件声明，外部无法注册静态映射。

这既是文档与实现不一致，也是金融场景“写死对端 MAC、跳过 ARP、防 ARP 欺骗”无法落地的原因。

### 3.2 同一网卡上的第二个 XDP 端点会静默降级

`xdp_attach_program` 使用 `XDP_FLAGS_UPDATE_IF_NOEXIST`，同一网卡已存在 XDP 程序时第二次 attach 必然失败；`SX_BACKEND_AUTO` 随后回退到内核 UDP，只有日志和事件能察觉。与此同时：

- `docs/manual.md:383` 写的是“多队列网卡可将不同流 RSS 到不同队列，每队列一个端点/进程”；
- `MEMORY.md` 的实测记录则明确写过“单网卡同时只能挂一个 XDP 端点”。

两者矛盾。在多进程网关或按队列分流的部署中，这会表现为“部分进程悄悄跑在 UDP 上”，是最难排查的一类性能事故。

### 3.3 组播/广播存在“收到数大于发送数”的既有异常

三节点测试记录中，发送 1000 条时出现过 `got=1033`、`got=1074`。测试程序在回调里逐条累加，库内部也有 `dup_packets` 计数，因此这不能简单归因于“环境重复包”，需要区分：

- 链路层重复（交换机/VBox 反射）；
- 库内重排环或来源表导致的重复投递；
- 测试进程重复入组或重复计数。

该问题直接影响“按序、去重”的对外语义，价值高于 RSS 与硬件时间戳，应优先归因。

## 4. 高价值 TODO 排序

排序原则：先修契约与正确性，再谈吞吐扩展，最后做测量增强。每项都给出验收口径，避免“做完但无法证明”。

```mermaid
flowchart LR
    A[P0 契约与安全<br/>静态 ARP/MAC] --> B[P0 性能开关<br/>拥塞控制开关]
    B --> C[P0 文档与行为一致<br/>多 XDP 端点限制]
    C --> D[P1 正确性归因<br/>组播重复投递]
    D --> E[P1 容量基线<br/>单核 PPS 实测]
    E --> F[P1 多队列设计<br/>共享 XDP 程序]
    F --> G[P2 测量增强<br/>硬件时间戳]
```

### P0-1 静态 ARP / 静态 MAC 落地（已完成）

要解决的问题：

- 对外提供静态映射注册能力，支持“对端 MAC 写死”；
- 静态项不可被 ARP 应答覆盖、不参与老化；
- 跨网段场景允许配置“网关 MAC”，避免把网关 IP 当作对端直接 ARP；
- 让 `sx_addr_t.mac` 不再是死字段，或明确废弃该字段并提供替代 API。

建议形态：新增 `sx_add_static_arp(ep, ip, mac)` 与 `sx_add_unicast_ex(ep, ip, port, mac)`；内部 ARP 项增加 `is_static` 标志，`arp_learn` 与老化路径跳过静态项。跨网段用独立配置项表达网关，不与“对端 MAC”混用。

验收：

- 抓包确认静态映射下不产生 ARP 请求；
- 注入伪造 ARP 应答后，静态项 MAC 不变；
- 跨网段经网关收发通过；
- 现有 `make check` 与 XDP 回环测试不回归。

成本：1~2 人日。风险：低。依赖：无。

### P0-2 拥塞控制开关（专线模式，已完成）

要解决的问题：内网专线不希望超时降窗把吞吐打回 1 个窗口；但必须保留 RTO 退避与重传，不能把“关 CC”实现成“关可靠性”。

建议形态：配置枚举 `sx_cc_mode_t { SX_CC_ON, SX_CC_OFF }`，默认 `ON` 保持兼容。`OFF` 时：

- 初始发送窗口直接取 `send_window`；
- 收到 ACK 不再增长窗口；
- 超时只做 RTO 退避，不将 `ssthresh/cwnd` 降为 1；
- 统计中暴露当前 CC 模式，便于现场确认。

验收：

- `SX_CC_OFF` 下 `cwnd` 恒等于 `send_window`；
- 丢包注入测试仍能重传并最终按序交付；
- `SX_CC_ON` 行为与当前版本逐项一致；
- 压测对比数据（吞吐、p99、重传数）写入文档。

成本：1 人日。风险：低。依赖：无。

### P0-3 修正“多 XDP 端点”的文档与可观测性（已完成）

要解决的问题：在完整的多队列方案落地前，先消除“静默降级”。

建议形态：

- 明确当前限制：同一网卡同一时刻仅支持一个 SX XDP 端点；
- 第二个端点 attach 失败时，除日志外触发 `SX_EVENT_BACKEND_CHOSEN` 并写入统计；
- 文档删除“每队列一个端点/进程”的现有表述，改为“当前不支持，规划中”；
- 若产品确实需要同机多端点，短期给出“多网卡 / 多 netns / 单端点多 conv”的替代方案。

验收：veth 上启动两个 `SX_BACKEND_XDP` 端点，第二个必须给出明确事件与统计，文档描述与行为一致。

成本：0.5~1 人日。风险：低。依赖：无。

### P1-1 组播/广播重复投递归因

要解决的问题：在不改变 best-effort 语义的前提下，确认“重复”来自链路、库内还是测试方法。

建议动作：

- 在接收侧增加分来源计数：线上唯一序号数、`dup_packets`、重排投递数、NACK 触发重发数；
- 用固定随机种子与单发送端复现，排除多接收进程互相干扰；
- 若确认库内重复，修正重排环/来源表的状态机，并补单测。

验收：三节点各接收端 `got == expect`，`dup_packets` 与抓包重复数可对账；单测覆盖“重发后再次收到已投递序号”的场景。

成本：2~3 人日。风险：中（涉及组播状态机）。依赖：P0 完成后再动，避免混入变量。

### P1-2 单核 PPS / 吞吐基线实测

要解决的问题：点评中的“单核 1400 万 PPS”目前没有仓库内证据，不能对外引用。

建议动作：

- 在真实网卡（非 veth）上分别测 UDP 后端与 AF_XDP zero-copy/copy；
- 固定报文大小、绑核、关闭中断干扰，记录 pps、带宽、重传、丢包；
- 结果写入 `docs/`，并注明网卡型号、驱动、内核、CPU。

验收：可复现的脚本与原始日志；数据能区分“单核上限”和“整机上限”。

成本：1~2 人日。风险：低。依赖：真实硬件。

### P1-3 多队列 / 共享 XDP 程序设计

要解决的问题：让同一网卡上的多个队列、多个端点（或进程）安全共存，而不是靠“第二个降级 UDP”。

建议先做设计验证，不直接写代码：

- 方案 A：libxdp multiprog + 共享 `xsks_map`，所有端点注册到同一 map 的不同队列键；
- 方案 B：单进程内多 xsk（每队列一个），由同一端点轮询；
- 方案 C：维持“一网卡一端点”，用多网卡/多 netns 横向扩展。

需要确认：XDP 程序生命周期归属、最后一个使用者退出时的 detach、ARP 由哪个队列处理、`XDP_SHARED_UMEM` 的收益与限制。

验收：设计文档给出选型结论与失败回退；原型在 veth 上验证两队列各自收包；不改变现有单端点性能。

成本：设计 2~3 人日，原型 5~10 人日。风险：高。依赖：P0-3、P1-2。

### P2-1 硬件时间戳（测量增强）

要解决的问题：区分“应用层 RTT”和“网卡到网卡的物理时延”。它不改善库的收发路径，只改善测量可信度。

路径：

- UDP 后端：`SO_TIMESTAMPING` + `recvmsg` 辅助数据；
- AF_XDP：内核 XDP metadata/hint 接口读取 RX 时间戳，需较新内核与驱动支持；
- 测试工具输出双时间轴：软件时间戳与硬件时间戳。

验收：在支持硬件时间戳的网卡上，能输出硬件 RX/TX 时间戳并与软件值对照；不支持时明确返回“不可用”，不静默填 0。

成本：3~5 人日。风险：中高（内核/驱动碎片化）。依赖：P1-2 的硬件环境。

### P2-2 亚毫秒 RTO（暂缓）

当前 `sx_now_ms` 为毫秒粒度，`min_rto_ms` 最小也只能到 1ms。若未来要支持 100~500us 的 RTO，需要把 KCP 定时路径改为微秒/纳秒时钟，并重新评估虚假重传。金融内网更常见的做法是保留毫秒级 RTO、依赖快速重传，因此该项暂缓，除非有明确的亚毫秒链路需求。

## 5. 不建议当前投入的方向

- 直接上 RSS 多队列代码：在“多端点共存”未解决前，多队列只会放大 attach 冲突。
- 直接上硬件时间戳：当前瓶颈是正确性归因与基线缺失，不是时间戳精度。
- 把“关闭拥塞控制”做成环境变量：与现有 `sx_config_t` 风格不一致，现场也不可观测；应做成配置枚举并进入统计。
- 用点评中的 PPS 数字对外宣传：没有仓库内实测支撑。

## 6. 建议执行顺序

1. P0-1 静态 ARP/MAC：先补安全与契约，改动小、收益直接。
2. P0-2 CC 开关：与 P0-1 可并行，互不冲突。
3. P0-3 文档与可观测性：顺手修正现有矛盾，避免现场误判。
4. P1-1 组播重复归因：在 P0 稳定后单独分支处理。
5. P1-2 真实硬件基线：为后续多队列与时间戳提供对照。
6. P1-3 多队列设计：先出设计结论，再决定是否投入原型。
7. P2 项按业务需求触发，不默认排期。

## 8. 验收总口径

- 功能：`make check`、`make check-xdp`、组播/广播三节点测试全部通过；
- 契约：头文件描述与实际行为一致，不再存在“写了但不用”的公共字段；
- 可观测：后端选择、CC 模式、静态 ARP 命中、重复包来源均可从统计或事件读取；

- 文档：限制与降级行为必须显式写出，不允许“静默回退”。
