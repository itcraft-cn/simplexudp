# 组播/广播跨机测试（101 发，102 多收）

日期：2026-10-02　后端：内核 UDP（`SX_BACKEND_UDP`）

## 1. 目标与环境

- 101（192.168.77.101）发送，102（192.168.77.102）开多个接收端，测试组播与广播。
- 环境：VirtualBox 两台 VM（debian001/002），测试网卡 enp0s9 同网段。
- 多网卡场景需显式指定组播接口：库新增 `sx_config.multicast_if`（UDP 后端据此
  `IP_ADD_MEMBERSHIP` 与 `IP_MULTICAST_IF`）。广播发送需 `SO_BROADCAST`（已补）。
- 测试程序：`tests/test_gsend.c`（发送）/ `tests/test_grecv.c`（接收，按序计数）。

## 2. 本地回环自检（库语义）

- 组播 `239.255.0.1:49000`：1 发 200，2 收均 **200/200**（ooo=0）。
- 广播 `255.255.255.255:49001`：1 发 100，1 收 **100/100**。

→ 库的组播/广播收发与顺序语义本身正确。

## 3. 跨机结果（101 发，102 三收）

### 组播（239.1.1.1:48000，1000 条）

```
mr1: got=1002 expect=1000 ooo=5
mr2: got=1001 expect=1000 ooo=3
mr3: got=865  expect=1000 ooo=4
```

- **可达**（mr1/mr2 收到约 1000），但存在两个问题：
  1. **重复投递**：`got > expect`（多收 1~2 条），说明接收去重不严格；
  2. **部分丢失未恢复**：mr3 少收 135 条，超出 NACK/高水位恢复能力或未在窗口内恢复。

### 广播（192.168.77.255:48001，1000 条）

```
br1/br2/br3: got=0
```

排查：
- 101 路由正确（`ip route get 192.168.77.255 -> dev enp0s9`），发送无报错；
- 一次抓包显示 101 的广播**确实到达** 102（10 个包，`192.168.77.101 > 192.168.77.255:48001`）；
- Python 原生 UDP 接收端在同端口上**收到** 25 个广播包；
- 但在多数受控运行中，102 抓包显示 **101 的广播未到达**（只有 102 自身 keepalive 广播），
  库接收端因此为 0。

→ **VirtualBox internal 网络的广播转发不稳定**（同代码在本地回环正常，Python 原生偶发可收），
并非库的收发逻辑缺陷。

## 4. 结论与建议

- **库侧**：回环下组播/广播正确；跨机组播可达但需解决“重复投递”和“丢失恢复不足”。
- **环境侧**：VirtualBox internal 网络对广播（以及部分组播）支持有限，不适合作为跨机组播/广播的
  可靠测试平台。建议：
  1. 改用**桥接网卡/物理交换/veth**做二层组播广播测试；
  2. 或对有可靠性要求的“点对多”改用**单播扇出**（对每个接收者 `sx_add_unicast`），
     库对单播是严格可靠有序的；
  3. 若必须组播，接收端接口需确保接受组播（`ip maddr add`/allmulti）。
- **待排查（库）**：组播引擎的重复投递（`got>expect`）与尾部/空洞恢复不足。
